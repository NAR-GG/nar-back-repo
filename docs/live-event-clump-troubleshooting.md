# 라이브 이벤트가 한 프레임에 뭉치고 같은 킬이 3개씩 저장된 문제

## 요약

라이브 경기 추적이 15~16분 끊긴 뒤 재개되면서, 그 구간의 이벤트 전부가 재개 시점 프레임 하나에서 발생한 것으로 기록됐다. 원인은 프레임 diff 기준(`lastObservedByGame`)이 끊기기 전 상태로 남아 있어 공백 구간을 한 번에 비교한 것이고, 뭉친 킬 델타를 그리디 페어링하면서 같은 킬이 서로 다른 `event_order`로 3~4건 복제됐다. 프레임 간 관측 연속성 검사를 넣어 공백이 감지되면 이벤트를 유도하지 않고 상태만 동기화하도록 고쳤다(PR #319).

이 문서를 읽으면 같은 증상을 다시 만났을 때 무엇부터 확인할지, 그리고 왜 배포를 의심하면 안 됐는지 알 수 있다.

## 증상

사용자 제보 두 건이 들어왔다.

07-27 케스파컵 T1 vs DNS 경기에서 이벤트가 3개씩 저장됐다. 07-28 케스파컵 DNS vs BRO 3세트에서는 알림이 한동안 오지 않다가 경기 끝날 때쯤 몰아서 왔고 몇 개는 누락됐다.

프로덕션 이벤트 API로 게임별 분포를 뽑으면 정상 경기와 문제 경기가 갈린다.

| 게임 | 이벤트 | 서로 다른 프레임 | 같은 킬 중복 |
|---|---|---|---|
| DNS vs T1 (07-27) | 41 | 10 | 3회 |
| GEN vs BFX (07-27) | 44 | 17 | 4회 |
| DNS vs BRO 3세트 (07-28) | 19 | 1 | 0 |
| DRX vs HLE | 82 | 80 | 0 |
| NS vs T1 | 81 | 78 | 0 |
| T1 vs DK | 63 | 59 | 0 |

정상 경기는 이벤트 수와 프레임 수가 거의 같다. 문제 경기만 프레임 수가 1/4 이하로 줄었다.

07-28 3세트는 19건 전부 `gameTime 421초` 한 점에 있었다. 타워 6개, 억제기 2개, 바론 1개, 드래곤 1개, 킬 9개가 같은 순간으로 기록됐다. 8분 경기에서 나올 수 없는 조합이다.

07-27 중복은 킬러와 피해자 조합까지 같았다.

```
(1389초, T1A Cypher → DNS Peter)    3회 저장
(1389초, T1A Cypher → DNS deokdam)  3회 저장
(1634초, GEN Ruler → BFX Kellin)    4회 저장
```

CloudWatch 로그에서는 07-28 3세트 이벤트 19건이 22:14:06부터 22:14:44까지 2.09초 등간격으로 저장됐다. 그 앞 44분간 저장 로그는 0건이다.

## 원인

세 단계가 이어져서 발생한다.

첫째, 업스트림(lolesports) 응답의 `liveGameIds`가 늦게 도착해 디스커버리가 진행 중인 게임을 놓쳤다. livestats 피드를 직접 조회해보면 21:50에 이미 프레임 27개와 `in_game` 상태를 주고 있었는데, 앱은 22:06:23에야 세트를 발견했다. 16분 지연이다.

```
startingTime(KST)   HTTP   프레임
21:35               204    없음
21:50               200    27개, in_game
22:00               200    25개, in_game
22:06:23            앱이 뒤늦게 세트 발견
```

기존에도 이 지연을 우회하는 코드가 있었다. `LivePollingScheduler.probeFeed`가 피드를 직접 찔러 진행 중 게임을 찾는다. 그런데 호출 조건이 `state == "unstarted"`였다. 이번 두 건은 `state`는 이미 넘어갔고 `liveGameIds`만 비어서 도착한 경우라 우회로를 타지 못했다.

둘째, 추적이 재개될 때 `LiveObjectEventRecorder`의 `lastObservedByGame`은 끊기기 전 상태를 그대로 들고 있다. 그 상태와 현재 프레임을 비교하면 공백 구간의 변화가 모두 현재 프레임의 변화로 잡힌다. 이벤트는 카운터 증가분으로 유도한다.

```java
// previous=2, current=8 이면 order 3..8 로 6건을 만든다
for (int order = previousValue + 1; order <= currentValue; order++) {
    saveEventIfAbsent(..., order, ...);
}
```

셋째, `recordKills`가 뭉친 팀 킬 델타만큼 킬러와 피해자를 펼쳐 그리디 페어링한다. 델타가 크면 같은 (킬러, 피해자) 조합이 여러 `order`에 배정된다. 멱등 키가 `(gameId, teamSide, eventType, eventOrder)`라 `order`가 다르면 DB 중복 검사를 통과한다. 그래서 같은 킬이 3~4건 저장되고 FCM 푸시도 그만큼 나갔다.

### 배포는 원인이 아니다

조사 초반에 무중단 배포를 두 번 의심했고 두 번 다 틀렸다.

07-27에는 배포가 0건이다. 07-26 15:02부터 07-28 00:06까지 배포 이력이 없는데 같은 증상이 났다.

07-28에는 `set-start(frame)` 로그(22:06:23)를 실제 게임 시작으로 읽어서 배포와 겹친다고 판단했다. 그 로그 자체가 이미 버그의 증상이었다. 피드를 직접 조회해 21:50에 이미 라이브였음을 확인하고서야 갈렸다.

## 해결

PR #319에서 세 가지를 고쳤다.

관측 연속성 검사를 추가했다. `previous`와 현재 프레임이 연속 관측인지 판정하고, 아니면 이벤트를 유도하지 않고 기준만 현재로 옮긴다.

```java
if (previous != null && !isContinuousObservation(previous, snapshot)) {
    log.warn("[live-notify] 관측 공백 감지 — 이벤트 유도 생략, 상태만 동기화 ...");
    previous = new ObservedObjectState(snapshot...);
    continue;
}
```

판정 기준은 프레임 시각 간격과 카운터 증가분이다. 프레임은 정상적으로 10초 간격으로 온다.

```java
MAX_FRAME_GAP_SECONDS = 60
MAX_KILL_JUMP = 5        // 에이스가 5킬
MAX_TOWER_JUMP = 2
MAX_BARON_JUMP = 1
MAX_INHIBITOR_JUMP = 2
MAX_DRAGON_JUMP = 1
```

`previous`를 현재로 옮기는 것이 중요하다. 옮기지 않으면 다음 폴링에서 같은 비교가 반복돼 계속 걸린다. 옮기면 그 다음 프레임부터 정상 10초 diff로 돌아온다.

킬 페어링 중복도 막았다. 피해자는 한 프레임에 한 번만 죽으므로, 같은 (킬러, 피해자) 조합이 반복되면 페어링이 잘못된 것이다.

```java
if (killerId != null && victimId != null && !pairsSeen.add(killerId + ">" + victimId)) {
    log.warn("[live-notify] 킬 페어링 중복 — 저장 생략 ...");
    continue;
}
```

피드 프로브 게이트를 넓혔다. `state == "unstarted"`에서 "업스트림이 라이브 게임을 모를 때(`liveGameIds`가 비어 있음)"로 바꿨다. `completed`는 디스커버리 대상이 아니라 제외해서 외부 호출이 늘지 않게 했다.

회귀 테스트 3개를 붙였다. 정상 간격은 저장하고, 비정상 점프(10초에 타워 6개와 킬 9개)와 프레임 공백(15분)은 저장하지 않는다. 가드 조건을 `if (false)`로 무력화하면 뒤 두 개가 실패한다.

### 해결되는 것과 남는 것

같은 킬 3개씩 저장은 없어진다. 가드가 뭉친 델타를 막고, 통과해도 페어링 중복 검사가 막는다.

가짜 버스트도 없어진다. 유도 자체를 하지 않으니 발송할 이벤트가 생기지 않는다. 실제 한타로 5킬이 10초에 나면 알림 5개가 몰아서 가지만 그것은 경기 그대로다.

알림이 한동안 오지 않는 증상은 그대로 남는다. 가드는 공백 구간 이벤트를 확정적으로 버린다. 공백 자체를 줄이는 것은 피드 프로브 게이트 확장의 몫이고, 배포 후 라이브 경기가 없어서 실효는 아직 검증하지 못했다.

임계값에는 오탐 여지가 있다. 베이스 레이스로 10초 안에 타워 3개가 실제로 떨어지면 그 프레임을 건너뛴다. 확률이 낮고 대가는 알림 몇 개 누락이라 가짜 3배 저장보다 낫다고 판단했다. 임계값은 상수라 조정하기 쉽다.

07-27 경기에 저장된 중복 행은 아직 남아 있다. 앱 타임라인에 같은 킬이 3~4번 보인다. 정리 쿼리가 필요하다.

## 배운 것

같은 증상을 다시 만나면 다음 순서로 확인한다.

1. 이벤트 API로 이벤트 수와 서로 다른 프레임 수를 비교한다. 정상 경기는 두 값이 거의 같다. 프레임 수가 훨씬 적으면 뭉침이다.
2. `set-start(frame)` 로그 시각을 실제 게임 시작으로 믿지 않는다. livestats 피드를 직접 조회해 언제부터 프레임이 있었는지 확인한다. 앱이 늦게 발견했으면 두 시각이 벌어진다.
3. 배포 이력을 먼저 확인해 상관을 배제한다. `gh run list --branch main`으로 충분하다.
4. `[live-notify] 관측 공백 감지` 로그가 있으면 가드가 작동한 것이고, 공백은 여전하다는 뜻이다. 로그가 없으면서 뭉침이 있으면 임계값이 느슨한 것이다.

livestats 피드는 과거 `startingTime`으로도 조회된다. 사고 시각의 피드 상태를 나중에 재현할 수 있다.

```bash
curl -s "https://feed.lolesports.com/livestats/v1/window/{gameId}?startingTime=2026-07-28T12:50:00Z"
```

인메모리 상태를 진실의 원천으로 쓰는 코드는 그 상태가 낡았을 때를 방어해야 한다. 이 버그의 핵심은 데이터가 틀린 것이 아니라 비교 기준이 낡았는데도 그대로 비교한 것이다.

## 조사 중 발견한 별건

같은 로그를 파다가 확인한 것들이다. 이 문서의 주제와는 별개다.

`LiveObjectEventRecorder.record()`가 `@Transactional` 안에서 FCM 발송을 동기로 한다. 이벤트당 2.09초가 걸리고, 그 트랜잭션이 `member`, `member_device`, `member_notification` 락을 쥔다. 07-28 21:30~22:03에 `Lock wait timeout exceeded` 22건이 났고 21:50에 8건이 몰렸다. 와탭 히트맵 응답시간 스파이크 시각과 일치한다.

`member_favorite_player` 유니크 제약 위반이 그대로 `GlobalExceptionHandler`까지 올라간다. 07-29 00:20~00:21에 3건 발생했고 사용자는 500을 받는다.

`discoverLiveGames`가 후보와 선정 결과를 로그로 남기지 않는다. 이번 조사에서 로그로 좁히지 못해 피드를 수동으로 조회했다.
