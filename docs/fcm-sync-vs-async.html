2026-09-06. FirebaseMobilePushGateway 가 sendEachForMulticast(블로킹)를 쓰고, 호출부(LivePollingScheduler)가 applicationTaskExecutor(가상 스레드)로 떼는 구조의 근거.

같은 점 / 다른 점

같은 점: FCM 왕복 시간 동일. …Async 는 네트워크를 빠르게 하는 게 아니라 "누가 기다리느냐"를 SDK 스레드풀로 옮기는 것. A 는 그걸 우리 가상 스레드가 한다.

A (지금)B (sendAsync)
기다리는 스레드가상 스레드 (블로킹 비용 ≈ 0)SDK 플랫폼 스레드풀
후처리 (마감·토큰 회수)순차 코드, try/catch콜백 체인. 예외·트랜잭션·MDC 컨텍스트 흘리기 쉬움
결과 필요 여부필요 — successTokens 로 누가 받았는지 기록결국 콜백에서 같은 일. 안 기다릴 수 없다
동시 청크순차 (1,500명 = 3회 직렬)청크별 future 모아 병렬 가능
결론: Java 21 가상 스레드에선 A 가 정석 — "동기 코드, 비동기 성능". B 는 플랫폼 스레드 시절의 답.
B 가 맞는 경우: 요청이 수백 개로 팬아웃되고 동시성 제어가 필요할 때. 우리 APNs 가 그 경우 — 멀티캐스트 없이 카드 1장 = HTTP 1회라 HttpClient.sendAsync + CompletableFuture 로 쐈고, #404 에서 HTTP/2 동시 스트림 한도 초과로 200장이 버려져 동시성 제어까지 넣었다.

  • FCM 청크 3개 직렬 → 병렬화 가치 작음 (왕복 3회 → 1회, 수백 ms)
  • 코드 주석: "dedup 예약과 발송 기록은 아직 구독자 단위 쿼리" → 1,500명이면 쿼리 1,500번. 이게 크다
  • 킬 알림(LiveObjectEventRecorder.fireLiveEventPush)은 executor 오프로드조차 없음 → 폴링 tick 을 막는다

우선순위: 킬 경로 오프로드(한 줄) > dedup 예약 배치화 > FCM 청크 병렬. sendAsync 전환은 셋 다 아니다.

이력

  • #323 (2026-07-29 실측): 구독자별 send 호출 → 1,500명 팬아웃 8~18분, 마지막 구독자는 세트 끝난 뒤 수신. 멀티캐스트 1회로 묶음. 이때 동기 SDK 그대로 두고 폴링 스레드 분리는 executor 로.
  • #345 / #404: APNs 는 CompletableFuture 팬아웃 + 동시 스트림 제어.
  • 기록된 "왜 sendAsync 안 썼나"는 없음. 결과적으로 맞는 선택이지만 의도된 결정이라기보단 관성.
