# 간헐 강제 로그아웃 조사

## 요약

"갑자기 로그아웃돼서 로그인 화면으로 튕긴다"는 신고의 원인은 하나가 아니라 서로 다른 구멍 5개였다. 2026-08-11부터 08-16까지 백엔드 3건, 모바일 2건의 PR로 5개를 모두 막았고, 아직 안 막은 구멍이 2개 남았다.

이 문서를 읽으면 각 구멍이 무엇이었는지, 어떤 PR이 무엇을 고쳤는지, 지금 남은 위험이 무엇인지, 그리고 고쳐졌는지를 어떻게 측정하는지 알 수 있다.

측정 방법이 도중에 바뀌었다. Sentry가 2026-08-06 이후 무료 쿼터 소진으로 이벤트를 받지 않는다. 지금 강제 로그아웃을 재는 지표는 Prometheus의 `/api/auth/refresh` 401 카운터다.

## 강제 로그아웃이 일어나는 조건

앱이 로그인 화면으로 되돌리는 경로는 두 개뿐이다.

1. `AuthService._forceLogout()` — 토큰 재발급이 "무효 확정"으로 실패했을 때
2. `splash_screen._proceed(null)` — 앱 시작 시 저장된 JWT를 못 읽었을 때

구멍은 전부 이 둘 중 하나로 수렴한다. 서버가 `/api/auth/refresh`에 401을 주면 1번, 앱이 Keychain 읽기 실패를 "토큰 없음"으로 오독하면 2번이다.

그래서 서버 쪽 지표 하나로 1번을 셀 수 있다. `/api/auth/refresh` 응답이 401이면 그 유저는 로그아웃됐다.

| 3 | 모바일 | 홈위젯 아이솔레이트가 앱과 동시에 재발급 → 2번을 유발 | mobile #174 |

### 1. 재발급 실패를 전부 로그아웃 처리

타임아웃(15초), 5xx, 네트워크 순단이 전부 `_forceLogout()`으로 갔다. 서버가 토큰이 죽었다고 말한 적이 없는데도 로그아웃시켰다.

`RefreshResult`를 세 갈래로 나눠 고쳤다. 재발급 응답이 401이거나 저장된 리프레시 토큰이 아예 없을 때만 `invalid`이고, 나머지는 `transient`다. `transient`면 그 요청만 실패시키고 다음 요청에서 다시 시도한다.

### 2. 토큰 회전의 늦은 조회 401

동시에 두 요청이 재발급을 시도하면, 먼저 도착한 쪽이 구 토큰을 지운다. 늦은 쪽의 `findByToken`이 그 뒤에 도착하면 401이고, 구멍 1번을 타고 로그아웃된다.

과거 수정(#329)의 벌크 삭제는 두 요청이 모두 조회에 성공한 경우만 구제했다. 삭제 커밋 뒤에 조회가 도착하는 순서는 그대로 401이었다.

삭제 대신 만료를 60초로 단축해서 고쳤다(`shortenExpiryByToken`). 구 토큰이 60초 더 살아 있어 늦은 쪽도 자기 토큰을 받는다. 쿼리 조건에 `expiresAt > :graceEnd`를 둬서 단축만 허용한다. 이미 grace에 들어간 토큰을 뒤이은 재사용이 다시 연장하지 못한다.

이 레이스는 이론이 아니라 실측이다. 2026-08-11 20:17 매치 종료 푸시로 분당 2,259 요청이 들어오자 HikariCP 기본 풀 10이 고갈됐다. SQL 자체는 5~65ms인데 커넥션 대기가 3~14초로 벌어졌고, 재발급도 5초를 기다리면서 레이스 창이 열렸다. 로그아웃 2건을 확인했다. 풀은 30으로 늘렸다(back #364).

### 3. 홈위젯 아이솔레이트의 동시 재발급

앱의 재발급 단일 실행 락(`_refreshing`)은 아이솔레이트 하나 안에서만 유효하다. 홈위젯 백그라운드 아이솔레이트는 별도 아이솔레이트라 락을 공유하지 않는다. 두 아이솔레이트가 동시에 재발급을 걸면 구멍 2번이 터진다.

과거 수정(#150)은 저장소 인스턴스만 공용화했고 락은 아니었다.

위젯 경로를 `_fetchMeWithoutRefresh()`로 분리해 고쳤다. 저장된 토큰만 쓰고, 실패하면 그 갱신 회차만 건너뛴다. 재발급도 로그아웃도 하지 않는다.

### 4. 로그인마다 세션 전량 삭제

로그인할 때마다 `deleteByMemberId`로 그 회원의 리프레시 토큰을 전부 지웠다. 같은 계정의 다른 기기가 다음 재발급에서 401을 받는다.

계정을 두 개 쓰면서 전환하는 사용 패턴에서는 전환할 때마다 발동했다.

전량 삭제를 없애고 세션을 공존시켰다. 무한 증식은 상한 5개로 막는다. 만료분을 먼저 청소한 뒤 상한을 넘는 만큼 가장 오래된 것부터 지운다.

### 5. 기기 잠금 중 Keychain 오류 오독

iOS는 기기가 잠겨 있으면 Keychain 읽기를 `-25308`(errSecInteractionNotAllowed)로 거부한다. 호출부가 이 실패를 "값이 없음"과 구분하지 못해 로그인한 유저를 비회원으로 판정했다. 스플래시에서 이 판정이 나면 곧바로 로그인 화면이다.

Sentry 기준 `splash_screen._bootstrap`에서만 873건 491명이었다.

읽기 함수를 둘로 나눠 고쳤다. `readOrThrowIfLocked`는 잠금이면 `SecureStorageUnavailableException`을 던지고 토큰에만 쓴다. `readOrNull`은 어떤 실패든 null로 접고, 못 읽어도 기본값으로 굴러가는 설정값에만 쓴다.

`_doRefresh`는 이 예외를 `transient`로 처리한다. 스플래시는 잠금이 풀릴 때까지 재시도한다.

쓰기 쪽도 같이 고쳤다. 접근성이 갈린 잔여 항목이 남아 있으면 write가 `-25299`(duplicate)로 튕겨서, 로그인은 성공했는데 토큰만 저장 안 되는 증상이 나왔다. `writeWithDuplicateRecovery`가 구 항목과 신 항목을 모두 지우고 재시도한다.

## 남은 구멍 3개

### A. 재발급 후 토큰 저장 실패 (서버에서 수정 중, PR #387)

앱은 재발급 200을 받은 뒤 새 리프레시 토큰을 Keychain에 쓴다. 이 쓰기가 기기 잠금으로 실패하면 앱은 구 토큰을 계속 들고 있는데 서버는 이미 회전을 마친 상태가 된다. grace 60초가 지나는 순간 그 구 토큰은 401이고, 앱은 401을 "무효 확정"으로 읽어 로그아웃한다.

`writeWithDuplicateRecovery`는 `-25299`만 복구하고 잠금은 다시 던진다. `_doRefresh`는 그 예외를 `transient`로 먹고 조용히 넘어간다. 그래서 앱은 자기가 구 토큰을 들고 있다는 사실을 모른다.

grace를 늘려도 창이 넓어질 뿐이다. 창을 여는 쪽은 회전 자체다.

back PR #387에서 회전 조건을 바꿨다. 잔여 수명이 7일보다 길면 회전하지 않고 같은 토큰을 그대로 반환한다. 만료가 임박한 토큰만 기존 회전 경로를 탄다.

회전을 없애도 되는 이유는 우리가 회전의 이득을 안 쓰고 있었기 때문이다. 회전의 보안 이득은 구 토큰 재사용 탐지인데, 우리 코드에는 그 탐지가 없다. 오히려 grace가 재사용을 정상 처리한다. 이득은 안 챙기고 레이스 비용만 내는 상태였다.

재사용 탐지를 붙이려면 감지 시 그 회원의 전 세션을 폐기해야 하는데, 그게 구멍 4번에서 없앤 동작이다. 오탐 한 번이 전 기기 로그아웃이라 득실이 안 맞는다.

Google, GitHub, Apple은 네이티브 클라이언트의 리프레시 토큰을 회전하지 않는다. Auth0와 Okta는 회전이 옵션이고 기본은 꺼져 있다. 회전이 사실상 필수인 쪽은 토큰이 XSS에 노출되는 브라우저와 SPA다.

### B. 접근성 마이그레이션 중 프로세스 사망 (미수정, iOS)

`migrateKeychainAccessibility()`는 구 접근성(`unlocked`) 항목을 `first_unlock_this_device`로 옮긴다. 옮기는 방법은 구 옵션으로 읽고, 지우고, 새 옵션으로 다시 쓰는 것이다.

```dart
await secureStorage.delete(key: entry.key, iOptions: legacyOptions);
try {
  await secureStorage.write(key: entry.key, value: entry.value);
} on PlatformException {
  // 새 옵션 write 실패 시 구 옵션으로 복원
}
```

`PlatformException`은 복원한다. 하지만 delete와 write 사이에 프로세스가 죽으면 복원할 코드가 실행되지 않는다. 토큰이 영구히 사라지고, 다음 실행에서는 마이그레이션이 빈 목록을 보고 완료 처리한다. 되돌릴 방법이 없다.

이 코드가 도는 시점은 앱 업데이트 후 첫 실행이다. 콜드 스타트에 마이그레이션과 캘린더 프리페치가 겹치는 순간이라 메모리 압박(jetsam)이 가장 큰 구간이고, 사용자가 스플래시에서 앱을 내리기도 한다.

현재 코드는 잠금 해제 상태에서만 마이그레이션을 돌려 확률만 낮춰놓았다.

고치려면 delete 전에 백업 키를 새 옵션으로 먼저 쓴다. write가 성공하면 백업을 지운다. 한 번 죽어도 다음 실행이 백업에서 복구한다.

### C. Android 저장소 오류를 전부 로그아웃 처리 (미수정)

`isKeychainLockedError`는 iOS 오류 코드만 본다.

```dart
return code.contains('-25308') ||
    code.contains('-25291') ||
    message.contains('User interaction is not allowed') ||
    message.contains('No keychain is available');
```

Android에서 복호화 실패나 키스토어 키 무효화가 나면 이 조건에 안 걸린다. `readOrThrowIfLocked`가 null을 반환하고, 스플래시는 그것을 "토큰 없음"으로 읽어 로그인 화면으로 보낸다. 구멍 5번의 Android판인데 #192는 iOS만 다뤘다.

`AndroidManifest.xml`에 `android:allowBackup="false"`가 없다. 기본값이 true라 Auto Backup이 켜져 있다. 기기를 바꾸거나 재설치해서 복원하면 암호문은 돌아오는데 키스토어 키는 안 돌아온다. 복호화가 실패하고 위 경로를 탄다.

코드에 `AndroidOptions` 설정이 하나도 없다.

### D. 스플래시 재시도 포기 (설계상 트레이드오프, iOS)

기기 잠금이 원인이면 스플래시는 횟수 제한 없이 잠금 해제를 기다린다. 잠금이 아닌데도 Keychain 읽기가 실패하면 몇 번 재시도하다 `_proceed(null)`로 로그인 화면에 보낸다.

무한 스플래시를 피하려고 mobile #193에서 상한을 뒀다. 남은 오탐 경로지만 의도한 선택이다.

## 측정 방법

### Sentry는 쓸 수 없다

Flutter 프로젝트의 마지막 이벤트가 2026-08-06 11:44다. 무료 쿼터가 조직 전체 월 5,000건이라 소진됐다. 백엔드 DSN은 08-15 관측 스택을 옮기면서 비웠다.

release 태그도 `1.0.7+13`에 고정돼 있다. Shorebird 패치가 릴리즈 번호를 안 올리기 때문이다. 그래서 Sentry로는 버전별 회귀 판정도 안 된다.

이 사실이 중요한 이유는 mobile #192가 Sentry 데이터를 근거로 작성됐기 때문이다. 그 데이터는 전부 08-06 이전이고, #174와 #365가 배포된 08-11보다 앞선다. 즉 #192의 근거는 앞선 수정들이 실패했다는 증거가 아니다.

### Prometheus로 재발급 401을 센다

`/api/auth/refresh`의 401은 강제 로그아웃 1건과 1:1로 대응한다. 이게 지금 유일한 직접 지표다.

```bash
curl -sG http://macmini:9090/api/v1/query --data-urlencode \
 'query=sum by (status)(increase(http_server_requests_seconds_count{uri="/api/auth/refresh"}[24h]))'
```

2026-08-16 실측값은 다음과 같다.

| 항목 | 24시간 |
|---|---|
| 재발급 성공(200) | 7,194 |
| 재발급 401 | 49 (0.68%) |
| 재발급 5xx | 0 |
| 로그인(소셜 4사 합) | 189 |

시간대별로 보면 새벽에는 401 비율이 0.2%인데 경기 시간대인 19시대에 1.5%로 3배 뛴다. 부하와 상관이 남아 있다는 뜻이다.

다만 iOS 릴리즈가 2026-08-15 16:19 UTC라 이 수치에는 구버전 잔존 유저가 섞여 있다. 앱 확산이 끝나는 3~4일 뒤에 다시 재야 깨끗하게 갈린다.

재발급 5xx가 0인 것도 의미가 있다. 재발급 데드락(Sentry BE-E, BE-D)의 마지막 이벤트가 08-06이고, 이는 back #365 배포 이전이다. 재발한 흔적이 없다.

### 앱 로그에는 토큰이 안 남는다

`LoggingFilter`가 `getRequestURI()`를 쓴다. 쿼리스트링이 빠지므로 Loki에는 `URI: [POST]/api/auth/refresh`만 찍힌다.

다만 리프레시 토큰을 query parameter로 보내고 있어서 EC2의 nginx access log에는 평문으로 남는다. Alloy가 컨테이너 로그만 수집하므로 Loki로는 안 나가지만, 디스크와 백업에는 쌓인다.

## 남은 과제

1. back #387 머지와 배포. 서버만 바꾸므로 구버전 앱 유저까지 즉시 적용된다.
2. 모바일에서 구멍 B와 C 수정. 백업 키 방식의 마이그레이션, Android 저장소 오류를 잠금 계열로 취급, `allowBackup=false`.
3. 리프레시 토큰을 query parameter에서 body로 이동. 서버가 먼저 둘 다 받게 하고, 앱 다음 릴리즈에서 전환한다.
4. `POST /api/auth/logout`이 아직 `deleteByMemberId`를 쓴다. 한 기기에서 로그아웃하면 다른 기기도 전부 로그아웃된다. 구멍 4번에서 로그인 경로만 고치고 로그아웃 경로는 남겨뒀다.
5. 08-19 이후 재발급 401 비율 재측정. 앱 확산이 끝난 뒤라야 #387과 #192의 효과를 볼 수 있다.

## 배운 것

로그아웃 신고를 받으면 먼저 두 경로 중 어느 쪽인지 가른다. 재발급 401이면 서버 쪽, 앱 시작 시 토큰 못 읽음이면 저장소 쪽이다. Prometheus의 `/api/auth/refresh` 401 카운터가 전자를 직접 센다.

null은 "값이 없다"와 "못 읽었다"를 구분하지 못한다. 로그인 여부처럼 null의 의미가 큰 값에서는 이 둘을 타입으로 갈라야 한다. 구멍 5번과 C가 같은 실수의 iOS판과 Android판이다.

토큰 회전은 재사용 탐지와 세트로만 의미가 있다. 탐지 없는 회전은 레이스만 만든다.

수정을 배포한 뒤 효과를 재려면 지표가 살아 있어야 한다. Sentry가 조용히 죽어 있던 열흘 동안 우리는 아무것도 측정하지 못했고, 그 사이에 작성된 PR은 열흘 전 데이터를 근거로 삼았다.
