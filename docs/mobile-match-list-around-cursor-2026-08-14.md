# 경기 리스트 커서 페이징 요청 회신 — `around` 로 처리했습니다

작성일: 2026-08-14 · 대상: `GET /api/mobile/matches` · 요청 문서: "경기 리스트 커서 페이징 요청 (모바일 앱)"

요청하신 **오늘로 진입 + 과거 방향 페이징**을 반영했습니다. 다만 `todayCursor` 대신
**`around`** 파라미터로 넣었습니다 — 왕복이 2회에서 1회로 줄고, 요청 문서에 있던 예외 규칙
두 개(가장 가까운 날짜 폴백, 오늘 커서의 경계 처리)가 필요 없어집니다.

`prevCursor` / `hasPrev` 는 **요청하신 이름 그대로** 내려갑니다.

## 확인한 것부터

보내주신 수치는 프로덕션 DB와 일치했습니다.

| 문서 | 실제 (2026-08-14 확인) |
|---|---|
| 2026 시즌 912경기 | 912 (2026-01-14 ~ 2026-09-19) |
| 2025 시즌 619경기 | 619 |
| 오늘 이전 778경기 → 16페이지 | 778 |

한 가지만 짚어두면, 778은 `seasonYear=2026` 이 걸린 값입니다. 앱이 시즌을 항상 보내므로
맞는 전제지만, 시즌 필터가 없으면 오늘 이전이 3,389건(68페이지)이 됩니다.

그리고 **"진입할 때마다 16번 이상 호출"은 아직 일어나지 않는 일**입니다. `sort` 파라미터가
서버에 없고 앱도 보내지 않아서, 현재 '오래된 순'은 서버 내림차순으로 받아 앱이 표시만
뒤집는 구조입니다(`match_list_viewmodel.dart` 의 `from: upcomingOnly ? _todayParam() : null`).
프로덕션 로그에서 실제로 관측되는 연속 왕복은 **9회**(`size=20` 인 구버전)이고,
`_pageSize = 50` 이 들어간 최신 빌드는 **3~4회**입니다.

즉 16페이지는 `sort=ASC` 를 서버가 지원하면 **새로 생기는** 문제였습니다. 그래서 정렬
파라미터를 추가하는 대신 진입 지점을 받는 쪽으로 방향을 잡았습니다.

## 반영 내용

### 요청 파라미터 2개 추가 (둘 다 선택)

| 파라미터 | 타입 | 설명 |
|---|---|---|
| `around` | `yyyy-MM-dd` | 그 날짜(KST 00:00)를 기준으로 **과거 절반 + 미래 절반**을 한 번에 |
| `before` | `string` | 그 커서보다 **과거**를 받음 (위로 스크롤) |

`around` / `before` / `cursor` 는 **서로 배타적**입니다. 두 개 이상 함께 보내면 400
(`INVALID_INPUT_VALUE`)입니다. 서버가 방향을 임의로 고르는 것보다 즉시 실패하는 편이
디버깅이 쉽다고 판단했습니다.

### 응답 필드 2개 추가

| 필드 | 타입 | 설명 |
|---|---|---|
| `prevCursor` | `string?` | 과거 방향 조회용. `before` 로 되던집니다. 더 과거가 없으면 `null` |
| `hasPrev` | `boolean` | 목록 앞쪽(과거)에 더 있는지 |

`todayCursor` 는 만들지 않았습니다 (이유는 아래).

## 사용 흐름

### 1. 진입 — 오늘 앞뒤를 한 번에

```
GET /api/mobile/matches?league=ALL&seasonYear=2026&size=50&around=2026-08-14
```

```json
{
  "league": "ALL",
  "matches": [ ...과거 25건, ...8/14 이후 25건 ],   // 과거→미래 순
  "prevCursor": "MjAyNi0wOC0wOFQwOTowMDowMHwxMTU1...",
  "hasPrev": true,
  "nextCursor": "MjAyNi0wOC0yMFQwOTowMDowMHwxMTY1...",
  "hasNext": true
}
```

`size=50` 이면 과거 25 / 미래 25입니다. 홀수는 미래쪽에 한 자리를 더 줍니다
(앵커가 "오늘"인 진입에서는 앞으로 볼 경기가 더 중요하다고 봤습니다). 한쪽이 부족해도
반대쪽으로 넘기지 않습니다 — 시즌 초라 과거가 8건뿐이면 8 + 25 = 33건이 옵니다.

### 2. 위로 스크롤 — 과거 이어받기

```
GET /api/mobile/matches?league=ALL&seasonYear=2026&size=50&before=<prevCursor>
```

응답 `matches` 는 **과거→미래 순**이라 기존 목록 앞에 그대로 붙이시면 됩니다(서버가 뒤집어
내립니다). 이어서 더 올라갈 때는 새 `prevCursor` 를 다시 `before` 로 보내면 됩니다.

`before` 응답의 `nextCursor` / `hasNext` 는 이미 들고 계신 구간을 가리킵니다. 값은 채워
보내지만 되던지면 받은 페이지를 다시 받게 되니, 위로 스크롤할 때는 `prevCursor` 만 쓰시면
됩니다.

### 3. 아래로 스크롤 — 미래 이어받기

미래 방향은 **기존 조합을 그대로** 쓰시면 됩니다. 전용 파라미터를 새로 만들지 않았습니다.

```
GET /api/mobile/matches?league=ALL&seasonYear=2026&size=50&from=2026-08-14&cursor=<nextCursor>
```

`from` 을 진입 때 쓴 `around` 날짜로 유지하면 같은 오름차순 축에서 이어집니다
(`from` + `cursor` 조합은 이미 지원되던 경로입니다).

## `todayCursor` 를 만들지 않은 이유

### 왕복 하나가 순수 낭비였습니다

요청안의 흐름을 펼치면 이렇습니다.

```
1회차: GET ?sort=ASC          → 1월 경기 50건(화면에 안 씀, 버림) + todayCursor
2회차: GET ?cursor=todayCursor → 8월 경기 50건(이게 쓰는 것)
```

16 → 2회는 맞지만, 2회 중 1회는 토큰 하나 받기 위해 시즌 첫 경기 50건을 받아서 버리는
호출입니다. `around` 는 1회차부터 화면에 쓸 데이터가 옵니다.

### 커서가 exclusive라 "오늘이 포함된 페이지의 커서"가 성립하지 않습니다

현재 커서 조건은 `matchDate > cursorDate OR (= AND id > cursorId)` 입니다. 커서는 "이 경기
**다음**부터"라는 뜻이라, 오늘 첫 경기의 커서를 드리면 **그 경기가 응답에서 빠집니다.**
정확히 하려면 "오늘 이전 마지막 경기"를 찾아 그 커서를 줘야 하고, 그 미묘함이 앱과 서버
양쪽에 남습니다.

`around` 는 경계가 경기 행이 아니라 **날짜**입니다(`match_date >= 앵커`). 누락될 여지가
구조적으로 없습니다.

### "가장 가까운 날짜" 폴백 규칙이 사라집니다

오늘 경기가 0건일 때 서버가 "가장 가까운 날짜"를 판정해야 했는데, `around` 는 날짜 기준이라
그날 경기가 없어도 앞뒤로 그냥 채워집니다. 판정 규칙도, `null` 폴백 분기도 필요 없습니다.

이 말은 앱 쪽 캐치업 루프(`_maxCatchUpPages = 20`)도 지울 수 있다는 뜻입니다. `todayCursor`
방식이라면 `null` 인 경우를 위해 그 루프를 폴백으로 남겨두셔야 했습니다.

### 의도는 요청에 담는 게 맞다고 봤습니다

`todayCursor` 는 앱이 "오늘로 가고 싶다"고 말하지 않았는데 서버가 모든 응답에 끼워 넣는
구조입니다. 최신순·'오늘 이후' 화면에서도 계산되고, 응답이 "오늘"에 의존하게 되어 나중에
이 엔드포인트에 캐시를 붙이면 매일 00:00 무효화가 필요해집니다. `around=2026-08-14` 는
요청 파라미터라 캐시 키에 자연히 포함되고, 안 보내면 비용이 0입니다.

## `sort` 파라미터에 대해

별건으로 요청하신 `sort=ASC|DESC` 는 이번에 넣지 않았습니다. `around` 가 있으면 진입 지점이
정렬을 함의하고(`from` 때 세운 원칙과 동일), 정렬 파라미터를 추가하면 `sort × from × around ×
before` 조합마다 커서 의미를 정의해야 합니다.

다만 **"오래된 순 = 시즌 처음부터"** 가 확정된 UX라면 이야기가 달라집니다. 지금 앱은 오래된
순을 기본값(`_sortOrderIndex = 1`)으로 두고 오늘로 스크롤하는데, 두 의도가 서로 당깁니다.
"오래된 순을 골랐다"를 "시즌 처음부터 보겠다"로 읽으면 오늘로 점프할 이유가 없고, "오늘 중심"이
맞다면 정렬이 아니라 진입 지점 문제입니다. 이 판단이 정리되면 `sort` 를 다시 논의하겠습니다.

## 하위 호환

**기존 앱은 변경 없이 그대로 동작합니다.**

- `around` / `before` 는 선택 파라미터입니다. 안 보내면 기존 분기를 그대로 탑니다
- 응답에 필드 2개가 추가되지만 앱 `MatchPage` 는 `matches` / `nextCursor` / `hasNext` 만
  읽으므로 무시됩니다
- 기존 필드·타입·의미는 건드리지 않았습니다
- `around`/`before` 없는 호출의 `prevCursor` 는 `null`, `hasPrev` 는 `false` 입니다
  (위쪽에 뭐가 있는지 계산하지 않습니다 — 확인 쿼리가 매 응답에 붙는 걸 피했습니다)

서버 먼저 배포하고 앱은 나중에 붙이셔도 됩니다.

  (`MobileMatchControllerTest`)
- `./gradlew test` 전체 그린

  `2026-08-13 11:00 UTC`, 미래쪽 첫이 `2026-08-14 07:00 UTC` 로 **중복도 누락도 없습니다**

## 구현 메모 (서버 내부)

새 JPQL 은 추가하지 않았습니다. 기존 DESC / ASC 쿼리를 양쪽에 한 번씩 씁니다.

과거쪽은 커서 조건을 쓰려면 `cursorId` 가 필요한데(null 이면 커서 조건 전체가 무시됨),
앵커와 `matchDate` 가 같은 행은 미래쪽이 담아야 하므로 **어떤 matchId 보다 작은 값**인 `"0"` 을
경계 id 로 넣습니다. `league_match.id` 는 전부 18자리 숫자 문자열이고 최소값이
`109466537707382618` 이라 문자열 비교에서 항상 `"0"` 보다 큽니다.
