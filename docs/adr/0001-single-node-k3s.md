# 단일 노드에 k3s 를 얹는다

맥미니를 서버로 만들 때(2026-08-13) 나는 문서에 이렇게 적었다 —
*"단일 노드 k8s 는 스케줄링과 HA 가 무의미하므로 학습 목적이 아니면 얹을 이유도 없다."*
닷새 뒤 얹었다(2026-08-18, #416~#422). 이 ADR 은 그 반전의 근거다.

**뒤집은 이유는 HA 가 아니라 선언적 운영이다.** HA 는 여전히 없다(노드 한 대).
얻은 것은 손으로 하던 다섯 가지가 파일로 내려온 것이다.

| 전 (docker) | 후 (k3s) |
|---|---|
| 블루-그린 포트 전환(8080↔8083)을 배포 스크립트가 `sed` 로 관리 | Deployment 롤링 교체 + `rollout undo` |
| CI 가 SSH 로 들어가 컨테이너를 갈아치움 | CI 는 이미지 push + `deploy` 브랜치에 태그 기록까지. 반영은 ArgoCD (#422) |
| `.env` 평문을 서버에 두고 관리 | sealed-secrets — 봉인본을 저장소에 두고 복호화 키는 클러스터 안에만 |
| nginx `nar.conf` 를 손으로 편집 | Traefik `IngressRoute` 선언 (#419) |
| 스케줄러를 웹과 같은 프로세스에 둘 수밖에 없었음 | Deployment 하나 추가로 분리 (#442) |

마지막 줄이 결정적이었다. docker 판에서 스케줄러를 떼려면 컨테이너·포트·배포
스크립트를 다 손봐야 했는데, k3s 에선 같은 이미지에 환경변수만 갈라 매니페스트
하나를 더 두면 끝이었다. 즉 **k8s 를 얹은 값은 "지금 필요한 것"이 아니라
"다음에 하고 싶은 게 싸진다"** 였다.

## 대가

- **응답이 6ms 느리다.** 같은 조건에서 `/api/matches` 가 파드 31ms, docker 25ms.
  DB 왕복이 49µs 더 걸리는데 이 API 가 요청당 쿼리를 64번 날려 증폭된다.
  k3s 문제가 아니라 N+1 문제라, 쿼리를 줄이면 같이 사라진다.
- **인메모리 상태가 파드 경계로 쪼개졌다.** 스케줄러를 뗄 수 있게 된 대가다.
  [ADR 0002](0002-scheduler-pod-split.md) 참고.
- Colima VM 안에 k3s 를 직접 설치했다(`colima --kubernetes` 아님). Colima 가 자기
  버전으로 덮어쓰지 않게 `kubernetes.enabled: false` 를 유지해야 한다.

## 되돌린다면

docker 판으로 되돌리는 비용은 이제 배포 파이프라인 전체다 — CI 가 SSH 를 잃었고
(#422), 시크릿이 봉인본으로만 존재하고, 라우팅이 Traefik 선언에 있다. 노드를 늘릴
계획이 없더라도 이 결정은 유지하는 편이 싸다.
